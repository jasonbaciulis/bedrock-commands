Commit the working changes on a new release branch, create a pull request to main, merge it when CI passes, and create a new release that Packagist publishes.

Running this command is my explicit request to stage, commit, push, merge and release.

## Check the package

1. Run `composer test`. If any step fails, stop and report the failure. Do not commit, push or release.

## Branch & commit the working changes

If `git status` shows no uncommitted changes, skip to "Create the release".

2. Run `git status` and `git diff` to understand all uncommitted (staged and unstaged) changes.
3. Create and switch to a new release branch off main: `git switch -c release/<short-descriptive-slug>` (kebab-case, derived from the overall theme of the changes).
4. Group the changes into logical commits — one commit per coherent unit of work, based on which files changed and what was changed together (e.g. a feature, a bugfix, a refactor, a config change should each be their own commit). Stage each group explicitly with `git add <paths>` rather than `git add .`.
5. Write each commit message following the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) spec:
   - Format: `<type>[optional scope]: <description>` — e.g. `feat(make): add --group-display option`.
   - Common types: `feat`, `fix`, `refactor`, `chore`, `docs`, `style`, `test`, `perf`, `build`, `ci`.
   - Keep it brief: a single sentence, lowercase, no trailing period — a clean one-liner in the GitHub UI.
   - Use `!` after the type/scope (e.g. `feat!:`) for breaking changes. See "Public contract" below for what counts as breaking.
   - Do not add a body or footer unless a change is genuinely breaking or needs context.
   - Do not mention it's generated by Claude.

## Create the pull request

6. Run `git log main..HEAD --oneline` to see the commits on this branch.
7. Run `git diff main...HEAD --stat` to see changed files.
8. Push the current branch: `git push -u origin HEAD`
9. Create a PR to main using `gh pr create --base main`. Write a concise title (under 70 characters) and a short description summarizing the changes. Use this format for the body, and leave out a section that has no bullet points:

```
## What's new
<bullet points>

## What's fixed
<bullet points>
```

Don't include anything else. Don't mention it's generated by Claude.

10. Return the PR URL.

## Merge the pull request

11. Wait for CI on the PR: `gh pr checks --watch --fail-fast`. If a check fails, stop and report which job failed (the matrix covers PHP 8.4/8.5 × lowest/highest dependencies). Do not merge.
12. Merge the PR into main: `gh pr merge --merge` (wait for it to complete). This ensures the new commits are on `main` before the release is tagged.
13. Switch back to main and pull the merged changes: `git switch main && git pull`.
14. Delete the merged release branch locally and on the remote: `git branch -d release/<short-descriptive-slug> && git push origin --delete release/<short-descriptive-slug>`.

## Create the release

15. Determine the current release version by running `git tag --sort=-v:refname | head -1`. The latest tag looks like `vX.Y.Z`. If there is no tag yet, the first release is `v1.0.0`; skip step 16.
16. Read the commits since the latest tag (`git log <latest-tag>..main --oneline`), recommend **major**, **minor** or **patch** based on the "Public contract" below, then ask me to confirm before you bump the version:
    - **major**: bump X, reset Y and Z to 0 (e.g. `2.0.0` → `3.0.0`)
    - **minor**: bump Y, reset Z to 0 (e.g. `2.0.0` → `2.1.0`)
    - **patch**: bump Z (e.g. `2.0.0` → `2.0.1`)
17. Create the release with `gh release create vX.Y.Z --target main --title "vX.Y.Z"`, using the new version. Use the same body format as the PR. Never add a `version` field to `composer.json`; Packagist reads the version from the tag.
18. Return the release URL.

## Check Packagist

19. Packagist updates from the GitHub hook within a minute. Check that the new version is listed: `curl -s https://repo.packagist.org/p2/jasonbaciulis/bedrock-commands.json | grep -o '"version":"vX.Y.Z"'`. If it is not there after a few minutes, tell me to check the hook on https://packagist.org/packages/jasonbaciulis/bedrock-commands.

## Public contract

Bedrock projects install this package with `^X.0`, so a change to any of these is breaking and needs a major release:

- Command names, arguments and options (`make:`, `delete:`, `rename:` × `bedrock-block`, `bedrock-set`). Bedrock's `.ai/guidelines/bedrock.md` tells agents to run them with exact arguments.
- Config keys in `config/bedrock-commands.php` and the config file name.
- The publish tags `bedrock-commands-config` and `bedrock-commands-stubs`, the published stub path `stubs/bedrock-commands`, the stub file names and the `{{ name }}` placeholder.
- The fieldset structure the commands expect: the grouped `blocks.yaml` and `article.yaml` with their entry fields.
- The minimum PHP or Statamic version.

A new command, option or config key with a default is minor. Classes in `src/Actions`, `src/Support` and `src/Enums` are internal, so changes there are patch or minor by their effect.
